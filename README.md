# Offline Autonomous Node Coordination

Minimal backend baseline for autonomous nodes that must keep working during long network outages and later reconcile state with explainable rules.

Requires Python 3.11 or newer and has no third-party runtime dependencies.

```bash
python -m offline_coordination status
python -m offline_coordination recovery check LEDGER [LEDGER ...]
python -m offline_coordination recovery run LEDGER [LEDGER ...] --keyring KEYRING --ticket TICKET --moment MOMENT --audit AUDIT
python -m offline_coordination recovery audit AUDIT [--after N] [--limit N]
python -m unittest discover -s tests -v
```

The baseline exposes a local status command plus offline ledger recovery operations. Persistent state is available via `offline_coordination.storage` and an append-only hash-chained audit log via `offline_coordination.audit`. Replication, conflict policies, security boundaries, observability, and network services are intentionally left for subsequent tasks.

## Ledger recovery

`offline_coordination.replication.recover_ledger(path)` settles one interrupted ledger transaction. Its `clean` result (no recovery intent) reports the SHA-256 of the current ledger bytes, lowercase hex, or `None` when the path is missing.

Two batch entry points operate on an explicit, non-empty list of distinct, non-empty ledger paths, validated in full before any file is read or modified (`TypeError` for container/element type faults, `ValueError` for an empty list, empty path or duplicate):

- `inspect_recovery(paths)` — read-only diagnostics. Each report carries `path`, `status`, `phase`, `digest`, `artifacts`, `action` and `error`: `clean` when no intent exists, `pending` with the suggested action (`rollback`/`complete`) and candidate/predecessor existence, digest-match and completeness when an intent is valid, `blocked`/`corrupt` when the intent or a necessary artifact is invalid, and `failed`/`os-error` when reading fails. Nothing is created, modified or deleted, and random artifacts are never scanned.
- `recover_many(paths)` — controlled batch recovery. Each ledger is recovered via `recover_ledger` in order; one failure never stops or rolls back the others. Successful items keep the `clean`/`rolled-back`/`completed` statuses; a `CorruptRecoveryError` becomes a `blocked`/`corrupt` item and an `OSError` a `failed`/`os-error` item, leaving enough intent and artifacts behind for an independent retry.

The module entry points `recovery check` and `recovery run` wrap these: they print exactly one line of compact UTF-8 JSON with recursively sorted keys, exit 0 when every ledger succeeds, 1 when any ledger is blocked or failed, and 2 on syntax or argument errors.

## Authorized recovery and the recovery audit

`offline_coordination.replication.recover_authorized(paths, keyring, ticket, moment, audit)` adds an authorization boundary and a durable operation audit around the same batch recovery. The ticket is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing newline, space or any other byte after the closing brace; it carries exactly `payload` and `signature`; the payload carries exactly `issuer`, `keyVersion`, `nonce`, `notBefore`, `notAfter` and the ordered `paths`, and the signature is the lowercase hex HMAC-SHA256 of the canonical compact payload encoding, verified against the keyring (the same version/secret/validity/revocation rules as `apply_signed_remote`, keys selected by exact issuer and version). The command paths must equal the ticket paths item for item — never expanded, reordered or normalized. Unknown credentials, a revoked, not-yet-valid or expired key or ticket, a path mismatch and a signature mismatch all raise `AuthenticationError` before any ledger is read, so a failed authorization creates no audit record, consumes no nonce and leaves no temporary file. An old-style ticket carrying a trailing newline (or any other non-canonical encoding) raises `ValueError`; field type faults raise `TypeError` (a `bool` never poses as `moment`); a malformed ticket key set, nonce, validity interval or signature format raises `ValueError`.

Once authorized, the batch runs in the `recover_many` order with the same per-ledger isolation and the same public item structure, and every step is recorded at the audit path as an append-only canonical JSONL hash chain, each record written, flushed and synced before the step it gates: a `batch` header on the first use of a nonce (binding the ticket digest, issuer and ordered paths), then a `before` record (original digest, phase, planned action) and an `after` record (new digest, status, failure category) per ledger. An `OSError` while reading the audit or writing, flushing or syncing a record propagates unchanged and leaves a consistent, retryable chain prefix. Re-entering with the same nonce and the same ticket reuses the recorded results and only continues the paths not yet settled — a process interrupted after a recovery but before its result record is completed from the recorded action and digests, without repeating side effects. The same nonce bound to a different ticket raises `ReplayError` (a `ValueError`) without modifying any file; a corrupt chain raises `CorruptRecoveryAuditError` (a `ValueError`).

`export_recovery_audit(path, after=0, limit=100)` pages the chain read-only (`after`/`complete`/`next`/`records`), validating the whole chain and treating a missing audit as an empty chain. The module entry point `recovery run` requires the four explicit materials `--keyring`, `--ticket`, `--moment` and `--audit` and exits 0 on success, 1 on ledger failures and 2 on authorization or argument errors; `recovery audit AUDIT [--after N] [--limit N]` prints one page of the chain.

`export_recovery_checkpoint(audit, keyring, issuer, version, moment)` adds an offline signature anchor that a later full-history replacement cannot recompute. It reads and validates the whole chain read-only and returns `bytes`: one compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing newline or any other trailing byte, carrying exactly `payload` and `signature`. The payload binds exactly `issuer`, `keyVersion`, `lastSeq`, `moment`, `tail` and `version` (integer 1) — `lastSeq` is the last chain seq (0 for a missing audit) and `tail` the last record hash (the zero hash for an empty chain). `signature` is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key the keyring binds to the exact issuer and version, with no fallback; unknown credentials and a revoked, not-yet-valid or expired key raise `AuthenticationError`, a corrupt chain raises `CorruptRecoveryAuditError`, and an `OSError` while reading propagates unchanged.

`verify_recovery_page(checkpoint, page, keyring, moment, cursor=None)` verifies a page dict against the checkpoint entirely offline — no file is read and no argument is modified. The checkpoint is parsed and its HMAC verified against the current keyring (exact issuer/version, usable at `moment`, so a later revocation or expiry rejects it); the bound `moment` is part of the signed payload itself. The first call passes no cursor and the page's `after` must be zero; later calls pass `{"digest", "next", "tail"}` built from the previous result, so `after` must equal the cursor `next`, the first record must chain to the cursor `tail`, and the cursor `digest` must equal this checkpoint's SHA-256 digest — a cursor can never resume another checkpoint. Each page's records must be contiguous from `after + 1` (no empty page, gap, reordering, duplicate or predecessor mismatch before the signed end), hash-correct within the page and across the paging boundary, and verification never crosses the signed `lastSeq`. The result carries `digest`, `lastSeq`, `status` and `tail`: reaching the signed tail is `verified`, every earlier page `continue`. An empty checkpoint accepts only an empty page starting at zero and directly reports seq 0, the zero hash and `verified`. Parameter or field type faults raise `TypeError` (a bool never poses as an int); keyring structure or format faults raise `ValueError`; checkpoint faults raise `InvalidRecoveryCheckpointError` and page or cursor faults raise `InvalidRecoveryPageError`, both `ValueError` subclasses.

`verify_recovery_checkpoints(items, keyring, moment)` verifies a whole batch of checkpoints offline and never reads a file. `items` is a non-empty list; each item contains exactly a non-empty, batch-unique `id`, the `checkpoint` bytes and the non-empty `pages` list holding that checkpoint's paging dicts in export order. The batch is validated in full before any item is verified — container, field or element type faults raise `TypeError` and an empty list, an empty or duplicate id, a wrong item key set or an empty page list raises `ValueError` (keyring and `moment`, a non-negative non-bool int, keep their usual classification). Each item is then handled in input order and in isolation: its pages are walked from a zero cursor through the exact `verify_recovery_page` rules, each cursor bound to the same checkpoint digest and the previous page's chain tail; keys are selected by the checkpoint's own exact issuer and version with no fallback, so checkpoints signed before and after a key rotation verify independently in one batch while the keyring retains both versions. Pages that reach the signed `lastSeq` must end there (any further page is a page fault); pages exhausted earlier are `incomplete` and keep the verified boundary. The result is a fresh dict with the fixed keys `items`, `version` (integer 1); each item report carries `id`, the checkpoint `digest`, the signed `issuer` and `keyVersion` (both null when the checkpoint does not parse), the verified `boundary` (`{"lastSeq","tail"}`, null when nothing was verified), a `status` of `verified`, `incomplete`, `invalid-checkpoint`, `invalid-page` or `unauthenticated`, and an `error` message (null exactly when verified). Only a batch-level or keyring-level fault raises — one item's failure never stops the later items, and no input is modified.

`adjudicate_recovery(items, policy, keyring, moment)` aggregates those per-site verifications into one offline verdict, reading no file and modifying no input. `items` is a non-empty list; each item contains exactly a non-empty, batch-unique `id` and `attestation` bytes. An attestation is a compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `payload` and `signature`; the payload binds exactly `batch`, `site`, `keyVersion` and `result` with no extra fields, where `result` has the single-item batch verification shape (`boundary`, `digest`, `error`, `id`, `issuer`, `keyVersion`, `status`). Every legal single-item result is accepted: a `verified` result always carries identity, a positive key version and a boundary, while a non-verified result may carry a null issuer/keyVersion (when the checkpoint did not parse) or a null boundary — its identity, digest, boundary and status are preserved — and only a `verified` result may count. `policy` is `{"batch", "sites", "threshold"}`: the authorized batch id, a positive threshold no greater than the site count, and a non-empty map of each authorized site to its non-empty set of allowed positive key versions; `keyring` and `moment` keep their existing structure, validity and revocation rules. The signature is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key selected by the exact site and version, with no fallback.

A batch or identity that is not authorized, unavailable/revoked/not-yet-valid/expired credentials, a wrong signature or a non-verified result each reject the packet with a fixed reason (`unauthorized-batch`, `unauthorized-site`, `unauthorized-version`, `credential-unavailable`, `revoked`, `not-yet-valid`, `expired`, `bad-signature`, `not-verified`) and never count; one packet with illegal encoding, key sets or fields is rejected alone as `invalid-attestation` without blocking the others. For one site an identical valid packet — the complete embedded result equal on every field — counts once and extra copies are `duplicate`; any different valid result (even one sharing digest and boundary) is a self-`contradiction`. Valid packets from different sites must agree on both digest and boundary — any disagreement is a fork a majority cannot outvote. The return is one canonical compact JSON object with the top-level keys `boundary`, `digest`, `items`, `status`, `threshold` and `version` (integer 1), no trailing byte: any contradiction or cross-site fork is `conflicted` with a null digest and boundary; a unique agreed result attested by at least the threshold of distinct sites is `accepted`; everything else is `insufficient`. Every packet stays in `items` — sorted stably by site then id — with its identity, conclusion (`valid`/`invalid`/`duplicate`/`contradiction`), fixed reason (null only for valid) and boundary, and the verdict does not depend on input order. Parameter, container or public field type faults raise `TypeError` (a bool never poses as an int); an empty list, duplicate id or illegal threshold, site or version rule raises `ValueError`.

`export_recovery_verdict(verdict, policy, keyring, issuer, version, moment)` signs that aggregate verdict for offline handover, reading and writing no file. It takes the canonical compact verdict bytes `adjudicate_recovery` returned, the same policy, a keyring, the signing issuer, key version and moment. It returns one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `payload` and `signature`; the payload binds exactly `batch`, `issuer`, `keyVersion`, `signedAt`, `policyDigest` and the complete `verdict`. The policy is canonicalized — sites in ascending order and each site's versions as an ascending array, all keys recursively sorted into compact UTF-8 — and `policyDigest` is its SHA-256; `signature` is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact issuer and version with no fallback. Unknown, revoked, not-yet-valid or expired credentials raise `AuthenticationError`. A non-bytes verdict or a wrong field type raises `TypeError` (a bool never poses as an int); a bad issuer, version or moment raises `ValueError`; an illegal verdict raises `InvalidRecoveryVerdictError`.

`verify_recovery_verdict(proof, policy, keyring, moment)` verifies such a handover proof entirely offline from just the proof, the policy, the current keyring and the verification moment — no file is read or written and no argument is modified. It recomputes the two digests, checks the batch, threshold, signing moment, proof/verdict structure and digest bindings, and re-checks the credentials against the current keyring (exact issuer/version usable at the verification moment, so a later revocation or expiry rejects it). It returns a fresh dict keyed `batch`, `issuer`, `keyVersion`, `signedAt`, `policyDigest`, `verdictDigest`, `status`, `digest`, `boundary`, `items` and `version` (integer 1). A non-bytes proof or a wrong public field type raises `TypeError` (a bool never poses as an int); an illegal policy, identifier, version or moment raises `ValueError`; an illegal verdict argument to `export_recovery_verdict` raises `InvalidRecoveryVerdictError`, while a bad proof structure — including an illegal verdict structure, field type or canonical encoding bound into the payload — a digest mismatch or a batch/threshold binding fault raises `InvalidRecoveryVerdictProofError` (both subclass `ValueError`); a bad signature or current credentials raise `AuthenticationError`.

`verify_recovery_verdicts(items, policy, keyring, moment)` verifies a whole batch of those handover proofs offline and never reads or writes a file or modifies an input. `items` is a non-empty list; each item contains exactly a non-empty, batch-unique `id` and the `proof` bytes. The batch is validated in full — container, element or public field type faults raise `TypeError` and an empty list, an empty or duplicate id or a wrong item key set raises `ValueError` — together with the shared `policy`, `keyring` and `moment`, which keep the single-entry validation and exception classification (a non-negative non-bool int) before any proof is verified; only such a batch-level fault raises. Each item is then verified independently, in strict input order, through the exact `verify_recovery_verdict` rules: one proof's failure never stops a later item or changes an earlier report, and each proof selects its key by its own exact issuer and key version with no fallback, so proofs bound to different issuers or rotations coexist in one batch. A currently revoked, not-yet-valid, expired or missing credential or a wrong signature makes that item `unauthenticated`; an illegal encoding, key set, field, digest, batch, threshold, signing moment or embedded verdict makes it `invalid-proof`; a passing proof is `verified`. The top-level result is a fresh dict with the fixed keys `items` and `version` (integer 1); each item report has the fixed key order `error`, `id`, `result`, `status`, where a verified item keeps `error` null and `result` a fresh copy of exactly the dict the single entry returns, and a failed item keeps a definite, non-empty copy of the original exception text with `result` fixed to null — the identity, digest and boundary of an unauthenticated payload never enter a result. Repeated calls return equal but mutually independent results.

`sign_batch_receipt(items, policy, keyring, moment, issuer, version)` signs one such batch verification into a receipt that can be handed over offline, reading and writing no file and modifying no input. It takes the same `items`, `policy` and `keyring` as `verify_recovery_verdicts`, the signing `moment` and the signing `issuer` and key `version`. The batch runs through the exact `verify_recovery_verdicts` rules: batch-level faults raise directly with the same `TypeError`/`ValueError` classification, while one proof's failure is only recorded in that item's report — a failed item keeps its original status, its error text and a null `result`, and no identity or boundary is ever filled in. The receipt is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `payload` and `signature`. The payload binds exactly `issuer`, `keyVersion`, `moment`, `policy`, `items` and `version` (integer 1): `policy` is the lowercase hex SHA-256 of the canonical compact policy encoding (sites ascending, each site's versions an ascending array), and each payload item — in the original input order, never sorted, deduplicated or replaced — carries exactly `id`, `digest` (the lowercase hex SHA-256 of that item's original proof bytes) and `report` (that item's batch verification report, bound verbatim). `signature` is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact issuer and version with no fallback; unknown, revoked, not-yet-valid or expired credentials raise `AuthenticationError`, and an empty issuer or non-positive version raises `ValueError`.

`verify_batch_receipt(receipt, policy, keyring, moment)` verifies such a receipt entirely offline from just the receipt bytes, the expected policy, the current keyring and the verification moment — no file is read or written and no argument is modified. It recomputes the policy digest and the signature, and checks the payload structure, the item order (each report's `id` must match its item's `id`), the item id uniqueness (a payload whose `items` repeat an `id` is rejected before any signature check), every report's shape and the moment binding, rejecting a receipt whose signing moment is later than the verification moment. The signature is checked against the key the *current* keyring binds to the payload's exact issuer and version, usable at the verification moment, so a later revocation or expiry rejects the receipt just as it does a replay. A non-bytes receipt or any field of the wrong type — including a `bool` posing as an `int` anywhere inside the signed payload or its bound reports — raises `TypeError`; an illegal policy, keyring or moment raises `ValueError`; an illegal encoding, key set, version value, digest format, duplicate item id, report shape or binding raises `InvalidBatchReceiptError` (a `ValueError` subclass); and invalid current credentials or a signature mismatch raise `AuthenticationError`. On success it returns a fresh deep copy of the payload; repeated calls return equal results that share no mutable object.

`delegate_batch_receipt(receipt, hops, policy, keyring, moment, issuer, version, audience)` signs the next hop of a delegation chain over an already-verified base receipt, reading and writing no file and modifying no input. The base `receipt` is verified through the exact `verify_batch_receipt` rules and the existing `hops` sequence (empty for the first hop) through the full chain contract before anything is signed. The new hop's `issuer` must equal the base receipt issuer (first hop) or the previous hop's audience, its `audience` must not be the issuer itself or any identity or target domain already in the chain, and its `moment` must not be earlier than its upstream's moment. The hop is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `payload` and `signature`; the payload binds exactly `issuer`, `keyVersion`, `moment`, `audience`, `upstream` (the lowercase hex SHA-256 of the base receipt or previous hop bytes) and `version` (the integer 1), and `signature` is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact issuer and version with no fallback. A wrong parameter type or any field of the wrong type inside the receipt or a hop — including a `bool` posing as an `int` — raises `TypeError`; an empty issuer or audience or a non-positive version raises `ValueError`; an illegal base receipt raises `InvalidBatchReceiptError`; an illegal delegation encoding, key set, version value or chain binding raises `InvalidReceiptDelegationError` (a `ValueError` subclass); and unknown, revoked, not-yet-valid or expired credentials raise `AuthenticationError`.

`verify_batch_receipt_chain(receipt, hops, policy, keyring, moment, target)` verifies a base receipt and its whole delegation chain offline from just the bytes, the expected policy, the current keyring, the verification moment and the expected receiving domain — no file is read or written and no argument is modified. The base receipt follows the exact `verify_batch_receipt` rules; each hop is then checked in order against the canonical delegation contract (exactly `payload` and `signature`, the fixed payload fields, the `upstream` digest chaining the base receipt or previous hop bytes, the first issuer equal to the base receipt issuer, each later issuer equal to the previous hop's audience, no self-delegation, no repeated identity or target domain, and no hop moment earlier than its upstream or later than the verification moment), and each hop's signature is checked against the key the *current* keyring binds to the hop's exact issuer and version, usable both at the hop's own moment and at the verification moment with no fallback. The last hop's audience must equal `target`. A wrong parameter type or any field of the wrong type inside the receipt or a hop — including a `bool` posing as an `int` — raises `TypeError`; an empty target, an empty hop sequence or a negative moment raises `ValueError`; an illegal base receipt raises `InvalidBatchReceiptError`; an illegal delegation encoding, key set, version value or chain binding raises `InvalidReceiptDelegationError` with the first failing hop in the message; and unknown, revoked, not-yet-valid or expired credentials or a signature mismatch raise `AuthenticationError`. On success it returns a fresh mapping with the fixed keys `hops` (the hop payloads in chain order), `receipt` (the base receipt payload), `receiptDigest` (the lowercase hex SHA-256 of the base receipt bytes), `target` and `version` (the integer 1); repeated calls return equal but mutually independent results.

`verify_batch_receipt_chains(items, policy, keyring, moment)` verifies a whole batch of those delegation chains entirely offline and adds the cross-chain delegation-fork entry point, reading and writing no file and modifying no input. `items` is a non-empty list; each item contains exactly a non-empty, batch-unique `id`, the `receipt` bytes, a non-empty `hops` list of hop bytes and a non-empty `target` str, and reports strictly preserve input order. The whole batch structure is validated together with the shared `policy`, `keyring` and `moment` — which keep their single-chain validation and classification — before any chain is processed: container, element or field type faults raise `TypeError` and an empty list, an empty or duplicate id, a wrong item key set or an empty hops list raises `ValueError`; only such a batch-level fault raises. Each item then runs independently through the exact `verify_batch_receipt_chain` rules, so one chain's failure never stops a later chain or changes an earlier report: a base-receipt fault is `invalid-receipt`, a delegation encoding, key-set, version-value or chain-binding fault is `invalid-delegation` and unknown, revoked, not-yet-valid or expired credentials or a signature mismatch are `unauthenticated`, each with the non-empty exception text and a null `result`. Successful chains are grouped by `receiptDigest` and only delegation paths under the same base receipt are ever compared; within one group, the same `upstream` digest pointing at two or more distinct legitimate next-hop audiences is a fork, while a plain prefix extension of one path is not. Every chain whose path crosses a forking edge is reclassified `conflicted`, keeping its verified single-chain result with `error` fixed to `forked-delegation`. The top-level result is a fresh dict with the fixed keys `forks`, `items` and `version` (integer 1); `forks` is sorted stably by `receiptDigest` then `upstream`, each entry carrying exactly `receiptDigest`, `upstream`, ascending `audiences` and the ascending `ids` of the chains crossing that edge, and each item report carries exactly `error`, `id`, `result` (a fresh independent copy of the single-chain result when verified) and `status`. Repeated calls return equal but mutually independent results.

`sign_receipt_fork_proof(items, policy, keyring, moment, issuer, version)` packages that fork summary into an offline-transferable signed evidence object, reading and writing no file and modifying no input. The `items`, `policy`, `keyring` and `moment` are exactly those of `verify_batch_receipt_chains`, which runs first; a proof is issued only when the resulting summary reports at least one fork (a fork-free summary raises `ValueError`). The proof is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing newline or any other trailing byte, carrying exactly `payload` and `signature`. The payload binds exactly `issuer`, `keyVersion`, `moment`, `policy` (the lowercase hex SHA-256 of the canonical compact policy encoding), the complete `report` and `chains`, and `version` (integer 1). `chains` summarizes every input chain strictly in input order with no reordering or omission: each entry carries exactly `id`, `digest` (the SHA-256 of that chain's base receipt bytes), `target` and `hops` (the SHA-256 of each hop's complete bytes in chain order). `signature` is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact issuer and version with no fallback; unknown, revoked, not-yet-valid or expired credentials raise `AuthenticationError`. A parameter or public field type fault raises `TypeError` (a bool never poses as an int); an empty issuer, a non-positive version, a negative moment or an illegal shared policy value raises `ValueError`.

`verify_receipt_fork_proof(proof, policy, keyring, moment)` verifies such evidence entirely offline from just the proof, the expected policy, the current keyring and the verification moment — no file is read or written and no argument is modified. It recomputes the policy digest, validates the proof encoding, key sets, version, digests, recursive key ordering, the chain-material order and references, the complete bound chain-batch report (item count and per-position ids, result receipt digest/target/hop count, hop upstream chaining, and the forking edges and crossing chains recomputed from the bound results), rejects a signing moment later than the verification moment, and checks the HMAC against the key the *current* keyring binds to the payload's exact issuer and version, usable at the verification moment, so later revocation or expiry rejects the proof with no fallback. On success it returns a brand-new mapping with the fixed keys `chains`, `issuer`, `keyVersion`, `moment`, `policyDigest`, `proofDigest` (the SHA-256 of the proof bytes), `report` and `version` (integer 1). A non-bytes proof or a wrong public field type raises `TypeError` (a bool never poses as an int); an illegal policy, keyring or moment raises `ValueError`; an illegal proof encoding, key set, version, digest, ordering, reference or report binding raises `InvalidReceiptForkProofError` (a `ValueError` subclass); unknown, revoked, not-yet-valid or expired credentials or a signature mismatch raise `AuthenticationError`.

`verify_receipt_fork_proofs(items, policy, keyring, moment)` verifies a whole batch of those proofs offline, never reading or writing a file or modifying an input. `items` is a non-empty list; each item contains exactly a non-empty, batch-unique `id` and the `proof` bytes. The batch and the shared `policy`, `keyring` and `moment` — which keep their single-proof validation and exception classification (a non-negative non-bool int) — are all validated before any proof is processed: container, element or field type faults raise `TypeError` and an empty list, an empty or duplicate id or a wrong item key set raises `ValueError`; only such a batch-level fault raises. Each proof is then verified independently through the exact `verify_receipt_fork_proof` rules, in strict input order, each selecting its key by its own exact issuer and version with no fallback: one proof's failure never stops a later proof or alters an earlier report, and a currently unknown, revoked, not-yet-valid or expired credential or a mismatched signature makes that item `unauthenticated`, an illegal encoding, key set, version, digest, ordering, reference or report binding makes it `invalid-proof`, and a passing proof is `verified`. The top-level result is a fresh dict with the fixed keys `items` and `version` (integer 1); each item report carries, in this key order, `error` (null exactly when verified), `id`, `result` (a fresh independent copy of the single-proof result when verified, otherwise null — the identity of an unauthenticated payload never enters a result) and `status`, each failure keeping a definite, non-empty copy of the original exception text. Repeated calls return equal but mutually independent results.

## Multi-site fork disposition decisions

`decide_forks(items, policy, keyring, moment, issuer, version)` turns those signed fork proofs into one multi-site disposition decision entirely offline, reading and writing no file and modifying no input. `items` is a non-empty list; each item contains exactly a non-empty, batch-unique `id` and non-empty `proof` bytes. `policy` contains exactly `action` (`"isolate"` or `"rollback"`), `base` (the existing `{"batch","sites","threshold"}` proof policy), `sites` (a non-empty map of each authorized non-empty site to its non-empty set of allowed positive key versions) and `threshold` (a positive integer no greater than the site count). Every proof is first verified through the existing receipt fork proof rules, then authorized by the exact signing site and key version with no fallback, then authenticated against the current keyring. An invalid, unauthorized or unauthenticated proof rejects only that item with one fixed reason (`invalid-proof`, `unauthorized-site`, `unauthorized-version`, `credential-unavailable`, `revoked`, `not-yet-valid`, `expired`, `bad-signature`) and never affects a later item; an identical proof digest counts once per site and extra copies are `duplicate`, while different valid proofs from the same site are a `contradiction`. The valid proofs of distinct sites must agree on every fork boundary made of the base receipt digest, the forking upstream and the target domain. A unique boundary set attested by at least the threshold of distinct sites is `accepted`, a contradiction or boundary disagreement is `conflicted`, and everything else is `insufficient`. An accepted decision recommends the policy action — isolate the deduplicated, ascending target domains, or roll back to before the fork — while every other outcome recommends `manual-review` and claims no boundary or target. The result is one canonical compact UTF-8 JSON object (recursively sorted keys, non-ASCII preserved, no trailing byte) carrying exactly `payload` and `signature`; the payload binds exactly `action`, `boundaries`, `decisions` (sorted by site then id), `issuer`, `keyVersion`, `policyDigest` (the SHA-256 of the canonical policy), `proofs` (each proof digest in the original input order), `recommendation`, `targets` and `version` (integer 1), and the signature is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact issuer and version with no fallback. Unknown, revoked, not-yet-valid or expired signing credentials raise `AuthenticationError`; a type fault (including a `bool` posing as an int) raises `TypeError`; an empty list, an empty or duplicate id or an illegal policy value raises `ValueError`.

`verify_fork_decision(decision, policy, keyring, moment)` re-checks such a decision entirely offline from just the decision packet, the expected policy, the current keyring and the verification moment — no file is read or written and no argument is modified. It validates the canonical encoding and key sets, recomputes the policy digest and the action binding, re-tallies the bound per-proof decisions (row ordering, the original-order proof digest bindings, duplicates, contradictions, cross-site boundary agreement, the threshold and the claimed boundaries, targets and recommendation) purely from the signed payload, and verifies the HMAC against the key the current keyring binds to the payload's exact issuer and version usable at the verification moment, so a later revocation or expiry rejects it. On success it returns a fresh dict keyed `action`, `boundaries`, `decisions`, `issuer`, `keyVersion`, `policyDigest`, `proofDigest` (the SHA-256 of the decision bytes), `proofs`, `recommendation`, `status`, `targets` and `version` (integer 1). An illegal encoding, key set, digest, ordering, reference or binding raises `InvalidForkDecisionError` (a `ValueError` subclass); unknown, revoked, not-yet-valid or expired credentials or a wrong signature raise `AuthenticationError`.

`verify_fork_decisions(items, policy, keyring, moment)` verifies a non-empty batch of those decisions offline and independently, in strict input order. Each item contains exactly a non-empty, batch-unique `id` and the `decision` bytes; the batch and the shared policy, keyring and moment are validated in full before any decision is verified, so only a batch-level fault raises (container/field faults `TypeError`; an empty list, an empty or duplicate id or a wrong item key set `ValueError`). Each decision is then reported in input order as `verified`, `invalid` or `unauthenticated` with the fixed key order `error`, `id`, `result` and `status`; a failed item keeps a definite, non-empty copy of the original exception text and a null result, and the identity of an unauthenticated payload never enters a result. Repeated calls return equal but mutually independent results. The existing proof interfaces and module commands are unchanged.

## Multi-site fork execution plans and confirmations

`plan_fork_execution(decision, policy, keyring, generated_at, expires_at)` turns one sealed, accepted fork disposition into a site execution plan entirely offline, reading and writing no file and modifying no input. The `decision` bytes are re-verified through the exact `verify_fork_decision` rules against the current keyring at the generation moment, and only an `accepted` decision can be planned — a `conflicted` or `insufficient` decision raises `ValueError`. The result is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `action`, `boundaries`, `decisionDigest`, `expiresAt`, `generatedAt`, `operations`, `policyDigest` and `version` (integer 1): it binds the decision and policy digests, the action, the inclusive validity window, every fork boundary and the deduplicated, ascending target domains — exactly one idempotent operation per target — and never copies an un-adopted proof (there is no `proofs`, `decisions` or signer field). Each operation carries exactly `action`, its target's `boundaries` (sorted), `operationId`, `requires` and `target`; the idempotent `operationId` is the lowercase hex SHA-256 over the decision digest, the action, the target domain and the canonical bytes of every related boundary. An `isolate` operation's precondition is exactly `{"state": "active"}` — the target domain must still be active — while a `rollback` operation binds `{"base", "upstream"}`, the base receipt digest and the forking upstream of its first boundary. Parameter, container or field type faults raise `TypeError` (a `bool` never poses as an int); a negative moment, a window with `generatedAt` after `expiresAt` or a non-accepted decision raises `ValueError`; an illegal decision packet raises `InvalidForkDecisionError`; unknown, revoked, not-yet-valid or expired decision credentials or a wrong signature raise `AuthenticationError`.

`confirm_fork_execution(plan, decision, policy, receipts, keyring, moment, issuer, version)` aggregates the per-site execution receipts into one signed multi-site confirmation, again entirely offline. It validates the plan packet, requires its `decisionDigest` to equal the SHA-256 of the offered decision bytes and its `policyDigest` to match the canonical policy, re-verifies the original decision against the current keyring (it must still be `accepted`) and checks that the plan regenerates byte-for-byte from the decision, the policy and its own window; the aggregation moment must not precede `generatedAt` but may lag past `expiresAt` after an outage. `receipts` is a non-empty list of canonical receipt envelopes kept in their collection order. Each receipt is one `{payload, signature}` packet whose payload binds exactly `planDigest`, `operationId`, `site`, `keyVersion`, `siteVersion`, `executionMoment`, `previous`, `result` and, for a success, `postDigest`; `result` is one of `executed`, `rejected` or `failed`, and only an executed receipt binds a post-state digest. The receipt site must equal the operation target and the key is selected by exact site and version with no fallback, required usable both at the execution moment and at the aggregation moment. A receipt for a replaced verdict, an unknown operation (or a site/target mismatch), an execution moment outside the plan window, a `previous` digest unequal to the SHA-256 of the operation precondition or an out-of-order same-site receipt rejects only that item with one fixed reason (`decision-replaced`, `unknown-operation`, `outside-validity`, `previous-mismatch`, `out-of-order`); credentials unknown, revoked or time-invalid at either moment, or a wrong signature, reject only that item as `bad-signature`; a structurally illegal receipt only records `invalid-receipt`. Identical receipt bytes count once and extra copies are marked `duplicate`; different valid results for one operation, or different executed post-state digests, are a `contradiction`. The precedence is contradiction → explicit site rejection → missing/failed operation → full success, yielding the overall statuses `conflicted`, `rejected`, `partial` and `confirmed` (a contradiction fails that operation regardless of other receipts). The result is one canonical compact `{payload, signature}` object with no trailing byte; the payload binds exactly `aggregatedAt`, `issuer`, `keyVersion`, the complete `plan`, the receipt digests in their original order (`receipts`), the per-item reason records (`reasons`, each carrying `digest`, `operationId`, `postDigest`, `result`, `reason` and `site`), the per-operation conclusions (`results`, in plan order with `operationId`, `result`, `target`), the overall `status` and `version`; the signature is the HMAC-SHA256 of the canonical payload bytes under the exact aggregator issuer/version key, following the same canonical encoding rules as the plan. Parameter/container/field type faults raise `TypeError` (a `bool` never poses as an int); an empty/null value or an illegal moment raises `ValueError`; plan/packet encoding, digest, ordering or binding faults raise `InvalidForkExecutionError` (a `ValueError` subclass), and unknown, revoked, not-yet-valid or expired aggregator credentials raise `AuthenticationError`.

`verify_fork_confirmation(confirmation, decision, policy, keyring, moment)` re-checks one confirmation entirely offline from just the packet, the original decision bytes, the policy, the current keyring and the verification moment — no file is read or written and no argument is modified. It validates the canonical encoding and key sets, regenerates the plan from the decision and policy and compares it to the bound plan, requires the aggregation moment not to be later than the verification moment nor earlier than `generatedAt`, re-derives the duplicate/contradiction markings, the per-operation conclusions and the overall status purely from the bound receipt digests (which must follow their original order) and reason records, and finally checks the aggregator HMAC against the exact issuer/version key usable at the verification moment, so later revocation or expiry rejects it. On success it returns a fresh mapping keyed `aggregatedAt`, `confirmationDigest`, `decisionDigest`, `expiresAt`, `generatedAt`, `issuer`, `keyVersion`, `operations`, `planDigest`, `policyDigest`, `receipts`, `reasons`, `results`, `status` and `version`. Type faults raise `TypeError`; an illegal policy, keyring or moment raises `ValueError`; an illegal encoding, digest, order or binding raises `InvalidForkExecutionError` (a structurally bad receipt is only recorded as `invalid-receipt`, never raised); unknown, revoked, not-yet-valid or expired credentials or a wrong signature raise `AuthenticationError`.

`verify_fork_confirmations(items, decision, policy, keyring, moment)` verifies a non-empty batch of those confirmations offline and in strict input order, in isolation. Each item contains exactly a non-empty, batch-unique `id` and `confirmation` bytes; the batch and shared decision, policy, keyring and moment are validated in full before any packet is verified, so only a batch-level fault raises (container/field faults `TypeError`; an empty list, an empty or duplicate id or a wrong item key set `ValueError`). Each packet is then reported as `verified`, `invalid` or `unauthenticated` with the fixed key order `error`, `id`, `result` and `status`; a failed item keeps a definite, non-empty copy of the original exception text and a null result, and the identity of an unauthenticated payload never enters a result. The top-level result has the fixed keys `items` and `version` (integer 1); repeated calls return equal but mutually independent results. The whole execution layer reads and writes no file and leaves every existing public interface and command unchanged.

## Multi-round fork convergence certificates

`certify_fork_convergence(rounds, decision, policy, keyring, moment, issuer, version)` certifies how one fork execution plan converged across several confirmation rounds, entirely offline, reading and writing no file and modifying no input. `rounds` is a non-empty list in chain order; each round carries exactly `seq` (the round number, consecutive from one), `previous` (the lowercase hex SHA-256 of the previous round's confirmation bytes, `null` for the first round) and the `confirmation` packet bytes. Every confirmation is re-checked through the exact `verify_fork_confirmation` rules at the certification moment and must bind the same plan, decision and policy; the aggregation moments must be strictly increasing across rounds, and a sequence gap, a broken chain link, a reordering or a duplicate is rejected. Each plan operation then converges in plan order: a `failed` round may advance to `executed` or `rejected` in a later round, but a settled execution or rejection must never be rolled back or swapped, and a re-execution binding a different post-state digest marks the operation `conflicted` — the settled evidence is kept, never overwritten by new evidence. One conflicted operation makes the overall status `conflicted`; otherwise an explicit rejection yields `rejected`, an unconverged operation `partial` and full convergence `confirmed`. Each result row carries exactly `operationId`, `target`, `result`, `settledRound` (null while unconverged) and `postDigest`, in plan order. The certificate is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `payload` and `signature`; the payload binds exactly `certifiedAt`, `decisionDigest`, `issuer`, `keyVersion`, `planDigest`, the per-round confirmation digests (`rounds`), the final `results`, the overall `status` and `version` (integer 1), and the signature is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact issuer and version with no fallback. Parameter, container or field type faults raise `TypeError` (a `bool` never poses as an int); an empty round list, a wrong round key set, an empty confirmation or an illegal moment, issuer or version raises `ValueError`; a broken round chain or convergence relation raises `InvalidForkConvergenceError` (a `ValueError` subclass); a bad confirmation raises `InvalidForkExecutionError`; unknown, revoked, not-yet-valid or expired credentials raise `AuthenticationError`.

`verify_fork_convergence(certificate, rounds, decision, policy, keyring, moment)` re-checks such a certificate entirely offline from just the certificate bytes, the original round chain and the shared materials — no file is read or written and no argument is modified. It validates the canonical encoding and key sets, re-walks the round chain (consecutive numbering, digest chaining, strictly increasing aggregation moments, one shared plan), re-verifies every bound confirmation at the certified moment, re-derives the per-operation convergence and overall status purely from the offered rounds, requires the bound round, plan and decision digests to match and the certification moment not to be later than the verification moment, and checks the HMAC against the key the current keyring binds to the payload's exact issuer and version, usable at the verification moment, so a later revocation or expiry rejects it. On success it returns a fresh mapping keyed `certifiedAt`, `certificateDigest`, `decisionDigest`, `issuer`, `keyVersion`, `planDigest`, `results`, `rounds`, `status` and `version` (integer 1). Type faults raise `TypeError`; an empty round list, a wrong round key set or an illegal policy, keyring or moment raises `ValueError`; a bad confirmation raises `InvalidForkExecutionError`; an illegal certificate encoding, key set, digest, round chain or convergence relation raises `InvalidForkConvergenceError`; unknown, revoked, not-yet-valid or expired credentials or a wrong signature raise `AuthenticationError`.

`verify_fork_convergences(items, decision, policy, keyring, moment)` verifies a non-empty batch of those certificates offline and in strict input order, in isolation. Each item contains exactly a non-empty, batch-unique `id`, the `certificate` bytes and the item's non-empty `rounds` chain; the whole batch — including every round chain of every item (its key sets, field types, non-bool sequence numbers and non-empty confirmation packet bytes) — and the shared decision, policy, keyring and moment are validated in full before any certificate is verified, so only a batch-level fault raises (container/field faults `TypeError`; an empty list, an empty or duplicate id, a wrong item or round key set or an empty round list or confirmation `ValueError`; a nested type fault inside any round rejects the whole batch before verification). Each certificate is then reported as `verified`, `invalid` or `unauthenticated` with the fixed key order `error`, `id`, `result` and `status`; only the round-chain links and the certificate itself remain a per-item concern; a failed item keeps a definite, non-empty copy of the original exception text and a null result, and the identity of an unauthenticated payload never enters a result. The top-level result has the fixed keys `items` and `version` (integer 1); repeated calls return equal but mutually independent results. The existing plan, confirmation, batch verification interfaces and module commands are unchanged.

## Multi-site offline convergence adjudication

`adjudicate_convergence(items, decision, policy, site_policy, keyring, moment, issuer, version)` turns single-site convergence certificates into one multi-site offline adjudication, reading and writing no file and modifying no input. `items` is a non-empty list; each item contains exactly a non-empty, batch-unique `id`, the `certificate` bytes and that certificate's non-empty `rounds` chain, and each item keeps the existing certificate identity and round-chain shape. `decision` is the original accepted fork decision bytes and `policy`/`keyring` are the shared fork materials used by the single-certificate rules. `site_policy` carries exactly `sites` (a non-empty mapping of each authorized non-empty signing site to its non-empty set of allowed positive key versions) and `threshold` (a positive integer no greater than the number of sites); `moment` is the current non-negative time and `issuer`/`version` name the adjudicator signing key. The whole batch — every round chain of every item, the shared materials and both policies — is validated in full before any certificate is reviewed: a nested type fault raises `TypeError` (a `bool` never poses as an int), while an empty round list or confirmation, a duplicate id or an illegal policy, threshold, moment, issuer or version raises `ValueError`.

Each certificate is then independently re-checked through the exact single-certificate rules (its canonical shape, the decision and certification-moment bindings and a full re-convergence of its rounds), authorized by the exact signing site and key version against `site_policy` with no key fallback, and authenticated against the current keyring. An invalid certificate, unavailable/revoked/not-yet-valid/expired credential, unauthorized site or version or wrong signature rejects only that item with the fixed fork-adjudication reason (`invalid-proof`, `unauthorized-site`, `unauthorized-version`, `credential-unavailable`, `revoked`, `not-yet-valid`, `expired`, `bad-signature`) and the later items still run. For one site, certificates with the identical complete convergence result — the plan summary, the overall status and every operation's result, settled round and post-state digest — count once and every extra certificate is a `duplicate`; certificates with different complete results are a `contradiction`. Distinct sites must agree exactly on the plan summary, the overall status and every operation's result, settled round and post-state digest. Any self-contradiction or cross-site difference is `conflicted` with the common result set to null and cannot be outvoted by a majority; a unique complete result attested by at least the threshold of distinct sites is `accepted` and keeps the full convergence result; every other case is `insufficient`.

The result is one canonical compact UTF-8 JSON object (recursively sorted keys, non-ASCII preserved, no trailing byte) carrying exactly `payload` and `signature`; the payload binds exactly `certificates` (each certificate digest in the original input order), `common` (the complete shared convergence result, null unless accepted), `commonDigest` (the SHA-256 of the canonical common result, null unless accepted), `decisionDigest` (the SHA-256 of the original fork decision bytes), `issuer`, `keyVersion`, the per-certificate `items` (sorted stably by site then id, each carrying its `certificateDigest`, `convergence`, `conclusion`, `id`, `keyVersion`, `reason` and `site`), `planDigest` (the accepted plan digest, null otherwise), `policyDigest` (the SHA-256 of the canonical site policy), `status` and `version` (integer 1). The signature is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact adjudicator issuer and version with no fallback; unknown, revoked, not-yet-valid or expired adjudicator credentials raise `AuthenticationError`.

`verify_convergence_decision(decision_packet, decision, site_policy, keyring, moment)` re-checks such an adjudication entirely offline from just the packet, the original fork decision bytes, the expected site policy, the current keyring and the verification moment — no file is read or written and no argument is modified. It validates the canonical encoding and key sets, recomputes the fork decision and site policy digests, re-tallies the bound per-certificate items purely from the signed payload (the stable site/id ordering, the original-order certificate digest bindings, the same-site duplicate/contradiction markings, cross-site agreement, the threshold, the plan digest and the common result and digest), and checks the HMAC-SHA256 against the key the current keyring binds to the payload's exact issuer and version, usable at the verification moment, so a later revocation or expiry rejects it. On success it returns a fresh mapping keyed `certificates`, `common`, `commonDigest`, `convergenceDecisionDigest` (the SHA-256 of the packet), `decisionDigest` (the bound fork decision digest), `issuer`, `items`, `keyVersion`, `planDigest`, `policyDigest`, `status` and `version` (integer 1). A non-bytes argument or a wrong public field type raises `TypeError` (a `bool` never poses as an int); an empty value, a duplicate id or an illegal site policy, threshold, moment, site or version raises `ValueError`; an illegal packet structure or binding raises `InvalidConvergenceDecisionError` (a `ValueError` subclass); unknown, revoked, not-yet-valid or expired credentials or a wrong signature raise `AuthenticationError`.

`verify_convergence_decisions(items, decision, site_policy, keyring, moment)` verifies a non-empty batch of those adjudications offline and in strict input order, in isolation. Each item contains exactly a non-empty, batch-unique `id` and the `decision` packet bytes; the batch and the shared fork decision, site policy, keyring and moment are validated in full before any packet is verified, so only a batch-level fault raises (container/field faults `TypeError`; an empty list, an empty or duplicate id or a wrong item key set `ValueError`). Each packet is then reported in input order as `verified`, `invalid` or `unauthenticated` with the fixed key order `error`, `id`, `result` and `status`; a failed item keeps a definite, non-empty copy of the original exception text and a null result, and the identity of an unauthenticated payload never enters a result. The top-level result has the fixed keys `items` and `version` (integer 1); repeated calls return equal but mutually independent results. The existing convergence certificate, plan, confirmation and batch interfaces, and the module commands, are unchanged.


## Supersession chains over convergence decisions

`supersede_decision(predecessor, evidence, decision, policy, old_policy, new_policy, keyring, moment, effective_at, issuer, version)` issues one signed successor packet that supersedes an existing convergence decision (the chain root) or the previous successor. `predecessor` is either packet; `evidence` is the stage's non-empty certificate/rounds list. The evidence sequence must have the predecessor as a strict prefix — a first successor keeps the root's certificates and ids in order, a later successor keeps every prior evidence item verbatim, so history is never deleted, changed or reordered; with an unchanged policy at least one new item is required, while a rotation may re-seal the same sequence. `decision`/`policy` are the original fork decision and shared fork policy, and `old_policy`/`new_policy` carry exactly `sites`, `threshold` and a positive integer `policyVersion`: unchanged sites and threshold keep the version, any change increments it by exactly one, and the root, plan and settled operations never change. The new verdict is recomputed from scratch from the full evidence: supplemental evidence moves `insufficient` to `accepted` or `conflicted`, an `accepted` verdict only keeps the identical common result or advances to `conflicted` (it never falls back to `insufficient` or swaps conclusions), and a `conflicted` verdict can never be masked by a later majority. The effective moment never moves backwards; the successor sealer and key version must be authorized by both policies and the credential must be usable both at `effective_at` and at the issuance `moment` (the same must hold for every evidence credential, or the settled verdict would differ at verify time). The packet is canonical compact UTF-8 JSON with exactly `payload` and `signature`; the payload binds the root digest, predecessor digest, height, the full recomputed verdict (certificate digests in original order, items sorted by site then id, status, common result/digest and plan digest), the raw evidence increment (bytes carried as lowercase hex), the old/new policy digests, the policy version, the effective moment, the issuer and key version and `version` (integer 1), signed with HMAC-SHA256 under the exact issuer/version key. Parameter or field type faults raise `TypeError`; an empty value, duplicate id, illegal version or backwards moment raises `ValueError`; a malformed root raises `InvalidConvergenceDecisionError`; a malformed successor or any broken chain rule raises `InvalidChainError`; an identity the policies do not authorize raises `InvalidChainError`; a signature or credential fault raises `AuthenticationError`.

`verify_decision_chain(root, successors, decision, policy, policies, keyring, moment)` verifies one chain hop by hop, entirely offline, reading and writing no file and modifying no input. `policies` provides one versioned site policy per stage (the root policy plus one per successor). The root is verified under the first policy's sites and threshold; every successor re-recomputes its verdict from the bound full evidence under its new policy at the hop's effective moment, re-checks the root, predecessor and height links, the old/new policy digests and version step, the non-decreasing effective moment and the append-only evidence prefix, re-applies the verdict state machine and dual-policy sealer authorization, requires the settled verdict to still hold with credentials usable at `moment`, and verifies the HMAC. It returns a fresh mapping with exactly `rootDigest`, `headDigest`, `height` (0 for a bare root), `policyVersion` and `status`; a bad root raises `InvalidConvergenceDecisionError`, a bad successor `InvalidChainError` and a signature or credential fault `AuthenticationError`.

`verify_decision_chains(items, decision, policy, keyring, moment)` verifies a whole batch offline. Each item holds exactly a unique `id`, its `roots` packet, its ordered `successors` packets and its per-stage `policies`; the batch and shared materials are pre-validated in full, so only batch-level faults raise (container/field faults `TypeError`; an empty list, empty or duplicate id or wrong key set `ValueError`). Each chain is then reported in strict input order, in isolation, as `verified`, `invalid` or `unauthenticated` with the fixed key order `error`, `id`, `result` and `status`. One predecessor digest pointing at two distinct successor digests is a fork; a mere prefix extension (one chain growing longer along the same packets) is not. Every verified chain crossing a forking edge is reclassified `conflicted` with its verified result retained; chains that were invalid or unauthenticated are never reclassified. The result has the fixed keys `items` and `version` (integer 1).

`seal_decision_head(items, target, decision, policy, keyring, moment, issuer, version)` seals a stable anchor only for the `target` chain within the batch that is `verified` (not conflicted by a fork), whose head is `accepted`. The anchor binds the target's root digest, head digest and height together with the head policy digest, head policy version and sealing moment and is signed under the exact issuer/version key; sealing a batch that is not entirely pre-validated, an unknown or empty target, a non-accepted/forked target or an illegal version raises `ValueError`, and a credential fault raises `AuthenticationError`. `verify_decision_head(anchor, items, target, decision, policy, keyring, moment)` re-checks the anchor structurally and its HMAC against the current key, re-runs the original batch and confirms the target still verifies, is accepted and unforked, and that every bound digest, height and version still matches; it returns `rootDigest`, `headDigest`, `height`, `policyDigest`, `policyVersion` and `anchorDigest`. A bad anchor raises `InvalidAnchorError` (a `ValueError` subclass); a batch fault raises the underlying `InvalidConvergenceDecisionError` or `InvalidChainError`; a signature or credential fault raises `AuthenticationError`. The adjudication, certificate, recovery command and `status` interfaces are unchanged and no new command-line entry is added.

## Pruning multi-round convergence archives

`plan_chain_prune(paths, checkpoint, decision, policy, keyring, moment)` builds a read-only signed plan for trimming persisted convergence archives, reading the archive files but never modifying, creating or deleting them. `paths` is an explicit, non-empty list of distinct file paths; each archive is one version-1 canonical JSON object (recursively sorted keys, non-ASCII preserved, exactly one trailing `\n`) carrying exactly `project` (a unique non-empty identifier), `certificate` and the ordered `rounds` (each `{confirmation, seq}`, numbered consecutively from one), with the certificate and every confirmation carried as non-empty lowercase hex bytes. The sealing `checkpoint` is a `seal_chain_checkpoint` packet authenticated against the current keyring through the exact `verify_chain_suffix` rules (exact issuer/version, usable at `moment`, no fallback). An archive is eligible for pruning only when its certificate digest is part of the checkpoint's pruned evidence prefix and its whole round group re-verifies through the exact `verify_fork_convergence` rules against `decision`, `policy` and `keyring` at `moment`; non-eligible archives are retained and when nothing is eligible a `ValueError` is raised. The result is one canonical compact `{payload, signature}` object with no trailing byte; the payload binds exactly `checkpoint` (its SHA-256), `delete` (eligible projects ascending), `retain` (the SHA-256 of every retained archive's bytes, ascending), `source` and `target` (each a map from an eligible project to the digest of its archive bytes before pruning and of its trimmed project-marker archive afterwards) and `version` (integer 1). It carries no moment or project identifier of its own and is signed with the checkpoint's own exact issuer/key, so equal arguments produce byte-identical plans. Container/field type faults raise `TypeError` (a bool never poses as an int); an empty/duplicate path or project, a wrong key set or an illegal version raises `ValueError`; a missing archive raises `FileNotFoundError`; an illegal archive or checkpoint raises `InvalidPruneError`; credential and signature faults raise `AuthenticationError`.

`prune_chain_archives(items, keyring)` executes the plans in one controlled batch. Each item holds exactly a unique non-empty `id`, an archive `path`, the signed `plan`, the sealing `checkpoint` and a `header` naming the exact signing `issuer`/`keyVersion` (the checkpoint sealer) and the non-negative prune `moment`; the batch structure and keyring are validated first. Each item then runs in strict input order and full isolation: bad credentials, malformed plans or checkpoints and stale archives are recorded for that item alone, the archive is left unchanged and the batch continues. When the archive at `path` hashes to the plan's source digest for its project, the planned trimmed target (one canonical `{project, version}` marker ending in one `\n`, the certificate and all round bytes gone) is installed in a crash-safe two-phase transaction, and the receipt status is `pruned`; when the archive already hashes to the target digest nothing is written and the status is `duplicate`; any other content records `StalePruneError`. An `OSError` raised while writing, flushing, syncing a file or directory, replacing or deleting is recorded for that item with its original text and leaves the retryable transaction material in place. The transaction uses only same-directory files — a unique candidate, the hard-linked predecessor and the `path + ".prune.txn"` intent — whose only phases are `prepared` and `installed`; unrelated files are never scanned or touched. The batch returns, in input order, fresh dicts keyed `id`, `receipt` and `error`. The receipt is one canonical compact `{payload, signature}` object binding the `status`, the complete plan, the `checkpoint` digest, `beforeDigest`/`afterDigest` (equal for a duplicate), the full `delete` and `retain` digests, the prune `moment` and `version` 1, signed under the exact header key. The first completion and a same-plan re-entry (an interrupted transaction whose `.prune.txn` intent is still present) return one identical signed receipt: an installed same-plan intent is completed to the original `pruned` receipt and a prepared one is rolled back and retried.

`recover_chain_prune(path)` settles one interrupted prune transaction, touching only the files its `path + ".prune.txn"` intent names. With no intent it returns `clean` without scanning artifacts, with the current archive digest (or `None` when the path is missing). A `prepared` intent rolls the source bytes back byte-for-byte from the retained predecessor (the path is removed again when it did not exist) and deletes the candidate, reporting `rolled-back`; an `installed` intent requires the current bytes to hash to `newDigest`, removes the remaining artifacts and reports `completed`; the intent is deleted last and the directory synced so a repeat returns `clean`, and every result carries the resulting digest. A non-str path raises `TypeError`; a malformed intent (wrong key set, version, phase, target, name confinement or digest binding, or a missing necessary artifact) raises `InvalidPruneError` without touching unrelated files; an `OSError` while reading, replacing, deleting or syncing propagates unchanged with the intent and artifacts retained for a retry. `InvalidPruneError` and `StalePruneError` both subclass `ValueError`. Planning and recovery read files but planning changes nothing; the existing checkpoint continuation verification, replacement chains, module commands and README command surface are unchanged.

`verify_prune_receipt(receipt, checkpoint, keyring, moment)` verifies one signed prune receipt entirely offline — only the receipt bytes, the sealing checkpoint bytes, the current keyring and a non-negative moment are consulted, no file is read and no input is modified. The receipt must be a version-1 canonical compact UTF-8 JSON object (recursively sorted keys, non-ASCII preserved, no trailing byte) carrying exactly `payload` and `signature`; the payload binds `afterDigest`, `beforeDigest`, `checkpoint`, `delete`, `moment`, the complete embedded `plan`, `retain`, `status` (`pruned` or `duplicate`) and `version`. The embedded plan must itself be the same canonical version-1 envelope, match the supplied checkpoint digest and signing identity/key version, and the receipt must repeat the plan's delete projects and retain digests exactly — a missing, extra, reordered or replaced entry is a broken binding. The checkpoint, plan and receipt signatures are all recomputed with the single key the checkpoint currently names (exact issuer/version, usable at `moment`) with no fallback. The unique plan target project is located solely from the status and before/after digests (zero or several candidates reject); the verifier then regenerates that project's version-1 prune marker itself, hashes its complete bytes, and requires the recomputed digest to match both the plan target and the receipt `afterDigest` — the receipt's derived conclusion is never trusted; a `pruned` receipt's `beforeDigest` must match the source archive and a `duplicate` receipt's both digests must match the target marker. It returns a fresh dict with the fixed key order `project`, `status`, `beforeDigest`, `afterDigest`, `checkpoint`, `planDigest`, `moment` and `version` (integer 1); repeated calls return equal, independent new objects. A wrong public argument type raises `TypeError` (a bool never poses as an int) and an illegal moment raises `ValueError`; an illegal encoding, key set, version, digest, status or binding raises `InvalidPruneReceiptError` (a `ValueError` subclass, distinct from `InvalidPruneError`); unknown, revoked, not-yet-valid or expired credentials or any signature error raise `AuthenticationError`.

`verify_prune_receipts(items, keyring, moment)` verifies a batch of prune receipts offline. Each item holds exactly a batch-unique non-empty `id`, the `receipt` bytes and the sealing `checkpoint` bytes; the non-empty list, keyring and moment are pre-validated in full, so only batch-level faults raise (container/field faults `TypeError`, a bool rejected as an int; an empty list, an empty or duplicate id, a wrong key set or an illegal moment `ValueError`). Each item is then verified in strict input order and in isolation through the exact `verify_prune_receipt` rules, reported as `verified`, `invalid` or `unauthenticated`; one item's failure never stops later items. The top-level result has exactly the fixed keys `items` and `version` (integer 1), and each report carries in fixed order `error` (`None` when verified, otherwise a definite non-empty message), `id`, `result` (a fresh single-entry result when verified, otherwise `None`) and `status`; repeated calls return equal but independent results.
## Signed prune attestations and multi-site threshold adjudication

`sign_prune_attestation(items, batch, keyring, moment, site, version)` hands the conclusion of a prune receipt batch verification to an offline adjudicator. It takes the same non-empty `items` list as `verify_prune_receipts` (each item exactly a batch-unique non-empty `id`, the signed `receipt` bytes and the sealing `checkpoint` bytes), the authorized non-empty `batch` id, a `keyring`, the signing `moment` and the exact signing `site` and key `version`. The batch runs through the existing `verify_prune_receipts` verification in full, so only batch-level faults raise (container/element/public-field type faults `TypeError`, a bool never posing as an int; an empty list, an empty or duplicate id, a wrong item key set, an empty batch or site or a non-positive/non-int version `ValueError`); one receipt's own failure is never raised. The `invalid` and `unauthenticated` items are kept exactly as the batch reported them — status, definite error text, a null `result` and all — and no trusted identity, project or boundary is ever filled in for them. The result is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `payload` and `signature`. The payload binds exactly `batch`, `items`, `keyVersion`, `moment`, `site` and `version` (integer 1); each item, in the original input order with no sorting, deduplication or replacement, carries exactly `checkpoint` (the lowercase hex SHA-256 of that item's checkpoint bytes), `id`, `receipt` (the SHA-256 of that item's receipt bytes) and `report` (that item's complete batch verification report, bound verbatim, with a verified report's result naming the same checkpoint digest). `signature` is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key the keyring binds to the exact site and version with no fallback; unknown, revoked, not-yet-valid or expired credentials raise `AuthenticationError`.

`adjudicate_prune_attestations(items, policy, keyring, moment, issuer, version)` aggregates uniquely identified site attestations into one signed threshold decision, reading and writing no file and modifying no input. Each item holds exactly a unique non-empty `id` and `attestation` bytes. The `policy` carries exactly `batch` (the authorized batch id), `sites` (a non-empty map of each authorized non-empty site to its non-empty set of allowed positive key versions) and `threshold` (a positive integer no greater than the number of sites); `keyring` and `moment` keep their existing rules and `issuer`/`version` name the adjudicator credentials. Every attestation is re-checked by the exact signing site and key version named in its payload with no fallback: a structurally illegal packet is recorded `invalid-proof`, unknown, revoked, not-yet-valid or expired credentials or a wrong signature `unauthenticated`, and a wrong batch, an unauthorized site or an unauthorized key version `unauthorized` — each rejecting only that item while the others continue. For one site, a packet counts only when the complete report and every receipt/checkpoint byte digest all agree; an exact repeat of the same content is `duplicate` and different valid content from one site is a `contradiction`. Distinct sites must agree on that same complete content: any cross-site report difference or bound-digest difference is a `conflicted` fork that a majority cannot outvote. A unique content backed by at least the threshold of distinct sites is `accepted` and carries the one common complete report; a contradiction or disagreement is `conflicted` with the common report null; a unique content below the threshold is `insufficient` and still carries the one common report, and only the absence of any valid vote leaves `insufficient` with the common report null. The result is one canonical compact UTF-8 JSON object with recursively sorted keys, non-ASCII preserved and no trailing byte, carrying exactly `payload` and `signature`; the payload binds exactly `attestations` (each input attestation's SHA-256 in the original input order), `issuer`, `items` (the per-attestation rows sorted stably by site then id, each carrying `conclusion`, the attestation `digest`, the authenticated `entries` or null, `id`, `keyVersion`, `reason` and `site`), `keyVersion`, `policyDigest` (the SHA-256 of the canonical compact policy — sites ascending, each site's versions an ascending array), `report` (the common complete `{items, version}` batch report, or null), `status` and `version` (integer 1); the signature is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the exact adjudicator key. Parameter, container or public-field type faults raise `TypeError` (a bool never poses as an int); an empty list, an empty or duplicate id, or an illegal batch, policy, threshold, moment, site or version raises `ValueError`; unknown, revoked, not-yet-valid or expired adjudicator credentials raise `AuthenticationError`.

`verify_prune_adjudication(adjudication, policy, keyring, moment)` re-checks such a decision entirely offline from just the decision bytes, the expected `policy`, the current `keyring` and the verification moment, reading and writing no file and modifying no argument. It validates the canonical encoding and every key set, recomputes the policy digest, and re-tallies the bound per-attestation rows purely from the signed payload: the original-order attestation digest bindings, the site/id row ordering, same-site duplicate and contradiction markings, cross-site report and digest agreement, the threshold outcome and the claimed common report — any structure, digest, ordering or tally mismatch raises `InvalidPruneAdjudicationError`, which subclasses `ValueError`. It then checks the HMAC-SHA256 against the key the *current* keyring binds to the payload's exact issuer and version, usable at the verification moment, so a later revocation or expiry rejects the decision with no fallback; unknown, revoked, not-yet-valid or expired credentials or a wrong signature raise `AuthenticationError`. On success it returns a fresh dict equal to the authenticated payload (`attestations`, `issuer`, `items`, `keyVersion`, `policyDigest`, `report`, `status`, `version`); repeated calls return equal but mutually independent objects sharing no mutable structure. A non-bytes adjudication or a field of the wrong type raises `TypeError` (a bool never poses as an int) and an illegal policy, keyring or moment raises `ValueError`. The existing chain pruning, recovery and receipt verification entry points and the README command surface are unchanged.

`verify_prune_adjudications(items, policy, keyring, moment)` re-checks a batch of signed prune adjudications entirely offline, reading and writing no file and modifying no input. Each item holds exactly a batch-unique non-empty `id` and `adjudication` bytes; `policy`, `keyring` and `moment` keep their existing rules. The whole batch structure is validated before any adjudication is parsed — container, element or field type faults raise `TypeError` (a bool never poses as an int) and an empty list, an empty or duplicate id or a wrong item key set raises `ValueError` — and only these batch-level faults raise: each adjudication is then verified in input order and in isolation through the exact `verify_prune_adjudication` rules, so one item's failure never stops later items or changes an earlier report. A passing adjudication is `verified`; an illegal encoding, key set, version, digest, ordering, tally or binding makes the item `invalid`; unknown, revoked, not-yet-valid or expired credentials or a wrong signature make it `unauthenticated`. The result is a fresh dict with the fixed keys `items` and `version` (the integer 1); each report preserves input order and carries, in this key order, `error` (null when verified, otherwise a definite non-empty message), `id`, `result` (a fresh single-entry result when verified, otherwise null) and `status`, and repeated calls return equal but independent results.

`sign_prune_adjudication_batch(items, policy, keyring, moment, issuer, version)` wraps that same batch verification into a signed package for offline handover, and `verify_prune_adjudication_batch(batch, policy, keyring, moment)` re-checks the package from just its bytes and the shared material. Signing runs the exact `verify_prune_adjudications` rules — batch-level faults raise directly while one adjudication's failure is recorded in its report with the original status, definite error text and a null `result`, and no identity, project or prune boundary is ever filled in from unauthenticated content. The package is one canonical compact UTF-8 JSON object (recursively sorted keys, non-ASCII preserved, no trailing byte) carrying exactly `payload` and `signature`; the payload binds exactly `issuer`, `items`, `keyVersion`, `moment`, `policyDigest` (the SHA-256 of the canonical compact policy) and `version` (the integer 1), where each item, in the original input order with no sorting, deduplication or replacement, carries exactly `digest` (the SHA-256 of that item's original adjudication bytes), `id` and `report` (that item's complete batch verification report, bound verbatim). `signature` is the lowercase hex HMAC-SHA256 of the canonical compact payload bytes under the key bound to the exact issuer and version with no fallback. Verification recomputes the policy digest and the signature against the current keyring and re-checks the payload structure, the item order (each report's `id` must match its item's `id`), every bound digest and every report's shape — a verified report's `result` must itself be a complete adjudication payload while a failed report keeps its error and a null result; a future signing moment, a duplicate id, a tampered report or a non-canonical encoding raises `InvalidPruneAdjudicationBatchError` (a `ValueError` subclass), an illegal policy, keyring or moment raises `ValueError`, a field of the wrong type raises `TypeError`, and unknown, revoked, not-yet-valid or expired credentials or a wrong signature raise `AuthenticationError`. On success a fresh deep copy of the authenticated payload is returned; repeated calls return equal but mutually independent objects. All three entry points read and write no file and modify no input; the README command surface and every other prune behavior are unchanged.
